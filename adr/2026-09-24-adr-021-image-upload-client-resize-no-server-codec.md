# ADR-021. 이미지는 브라우저가 줄이고 서버는 검사 · 저장만 한다 — 이미지 코덱 의존성 없음

- 날짜: 2026-09-24
- 상태: 승인됨

## 문제 (맥락)

이미지 올리기(이슈 #82, M5를 당겨 옴)에서 "긴 변 1600px로 줄이기"가 필요하다(NATURAL_SIZE_RANGE, plan 3-8). Node 내장 모듈에는 JPEG · PNG · WebP를 풀고 다시 굽는 코덱이 없다. 서버에서 줄이려면 sharp(libvips 네이티브 바이너리) 같은 새 의존성이 필요하다.

plan 3-8은 이미 방향을 정해 두었다: "클라이언트에서 리사이즈 · WebP 변환(긴 변 1600px, 1MB 이하) → presigned URL로 S3에 직접 업로드 → 경로만 문서에 넣는다". 배포(M4)에서 파일은 API 서버(Lambda)를 거치지 않는다. 그렇다면 서버 쪽 코덱은 로컬 개발에서만 쓰이게 된다.

## 결정

- **줄이기와 WebP 변환은 브라우저가 한다**(에디터, 이슈 P9 — `createImageBitmap` + canvas `toBlob("image/webp")`). 서버는 줄이지 않는다.
- 서버는 **검사와 저장만** 한다.
  - 형식: 헤더의 매직 바이트를 직접 읽어 JPEG · PNG · WebP · GIF만 받는다. 확장자와 Content-Type은 믿지 않는다. SVG는 받지 않는다(스크립트를 품을 수 있다).
  - 크기: 헤더에서 가로 · 세로를 읽는다. 긴 변이 1600px을 넘으면 422로 거절하고 "줄여서 다시 올리라"고 알린다. 원본 크기는 응답으로 돌려준다(이미지 블록 `naturalWidth/Height`).
  - 방향: 브라우저 파이프라인은 캔버스로 다시 그리면서 EXIF 방향을 픽셀에 굽는다는 것을 전제로 한다. 서버는 JPEG EXIF Orientation이 5~8(가로 · 세로가 뒤바뀌는 방향)이면 422로 거절한다 — 헤더 크기 그대로 저장하면 원본 크기가 뒤바뀐다.
  - 용량: 1 MiB 상한(plan 3-8 "1MB 이하"), 넘으면 413.
  - 이름: 내용 SHA-256 앞 32자 + 형식 확장자(`/images/<해시>.webp`). 같은 파일은 같은 경로라 중복 저장이 없다.
- 저장은 `ImageStore` 인터페이스 뒤에 둔다(`put(name, bytes, contentType)`). 저장한 이미지를 직접 내주는 구현(S3 + CloudFront 포함)은 응답에 Content-Type · `nosniff` · `Content-Security-Policy: default-src 'none'; sandbox`를 붙여야 한다 — 로컬 `GET /images/*`와 같은 방어. 지금은 로컬 파일 구현(`<root>/images/`)만 있다. M4에서 S3 구현 또는 presigned 발급으로 바꾸고, 형식 · 크기 검사는 같은 `probeImage`를 쓴다.
- 새 의존성은 없다. 헤더 읽기는 레포 안의 작은 순수 함수(`image-probe.ts`)다.

## 버린 대안

- **서버에서 sharp로 줄이기**: 어떤 파일을 올려도 서버가 맞춰 주므로 가장 편하다. 하지만 네이티브 바이너리 의존성(플랫폼별 prebuild, Lambda 번들 크기 · 콜드 스타트)이 생기고, 배포에서는 presigned 직접 업로드라 쓰이지도 않는다. 로컬에서만 쓰는 무거운 의존성이라 LIBRARY 게이트 1(문제로 시작하는가 — 배포 경로에는 이 문제가 없다)과 3(직접 구현이 더 싸지 않은가 — 서버는 헤더만 읽으면 된다)을 통과하지 못한다.
- **image-size 같은 헤더 읽기 라이브러리**: 형식 네 가지의 헤더만 보면 되고, 필요한 바이트 위치는 각 형식 명세에 고정되어 있다. 테스트로 고정한 수십 줄이 의존성 하나보다 싸다.
- **서버 없이 브라우저가 로컬 파일 시스템에 저장**: 에디터와 사이트가 같은 경로(`/images/…`)로 이미지를 보려면 서버가 제공해야 한다.

## 감수한 트레이드오프

- API를 직접 부르는 클라이언트(스크립트, 나중의 MCP 도구)는 스스로 줄여서 올려야 한다. 422 메시지로 무엇을 할지 알려 준다.
- 애니메이션 GIF는 브라우저 canvas가 첫 프레임만 굽는다. 1600px 이하이고 1 MiB 이하면 변환하지 않고 원본을 그대로 올리면 된다(P9에서 처리).
- 헤더만 보고 파일 전체가 올바른지는 확인하지 않는다. 깨진 파일은 브라우저에서 안 그려질 뿐 보안 경계는 아니다. 이미지는 `<img>`로만 쓰이고, `X-Content-Type-Options: nosniff`와 형식에 맞는 Content-Type으로 준다.
- 서버가 내주는 이미지의 방어 헤더는 로컬 라우트에만 코드로 있다. M4에서 CloudFront가 직접 내주면 같은 헤더를 응답 헤더 정책으로 다시 설정해야 한다(저장소 계약 JSDoc에 적어 둠).
- 이미지 경로에 워크스페이스가 없다(`/images/<해시>`). 1단계는 계정 하나라 문제가 없고, 내용 해시라 워크스페이스끼리 겹쳐도 같은 파일이다.

## 재검토 조건

- 브라우저 줄이기의 품질이나 호환성(Safari WebP 인코딩 등)이 실제로 문제가 될 때
- 사용자가 아닌 경로(MCP로 AI가 이미지 올리기, 가져오기)에서 줄이지 않은 원본을 받아야 할 때
- M4 배포에서 presigned 업로드 대신 API 경유 업로드를 쓰기로 할 때
- 브라우저가 EXIF 방향을 굽지 않는 경로(원본 JPEG를 그대로 올리는 도구)가 생길 때
