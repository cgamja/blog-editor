# ADR-012. 정규화 멱등성 같은 불변식은 fast-check 속성 기반 테스트로 검사한다

- 날짜: 2026-09-23
- 상태: 승인됨 · 일부 대체 → adr-015(생성기를 `./testing` 진입점으로 공유)
- 원천: plan 05 Harness(속성 기반 층 "도입 시 검증") · plan 11 M0 스파이크 표 "fast-check LIBRARY 게이트" · `.claude/rules/editor.md`("정규화는 멱등 — 속성 기반 테스트 대상") · 이슈 #2 · #5

## 문제 (맥락)

`normalize(doc)`는 "임의의 유효 문서에 두 번 적용해도 같다"가 계약이다. 손으로 만든 예제 몇 개는 마크 조합 · 중첩 목록 · 꾸미기 속성의 조합 공간을 덮지 못하고, 뒤에 올 불변식(zod ↔ ProseMirror 스키마 일치, doc → md → doc 보존 범위)도 같은 모양이다. 생성기로 문서를 만들어 불변식을 검사하는 도구가 필요하다.

## 결정

- `fast-check`를 루트 devDependency로 추가한다(Vitest와 같은 자리). 테스트 전용이며 번들에 들어가지 않는다.
- LIBRARY 게이트(cgamja `docs/spec/LIBRARY.md`) 검진 — 2026-09-23 기준:

| 항목        | 값                                                           | 판정      |
| ----------- | ------------------------------------------------------------ | --------- |
| 유지보수    | v4.10.2, 마지막 릴리스 2026-09-19                            | 통과      |
| 사용 규모   | JS 속성 테스트의 사실상 표준(Jest · Vitest 문서가 예시로 씀) | 통과      |
| 번들 크기   | devDependency — 런타임 번들 영향 없음                        | 해당 없음 |
| 전이 의존성 | `pure-rand` 1개                                              | 통과      |
| 보안        | `pnpm audit` high/critical 없음(설치 시 확인)                | 통과      |
| 타입        | TS 내장(`lib/fast-check.d.ts`)                               | 통과      |
| 모듈 형식   | ESM + CJS, Vitest node에서 동작                              | 통과      |
| 라이선스    | MIT                                                          | 통과      |

- 생성기(arbitrary)는 테스트 파일 옆에 두고 패키지 `index.ts`로 export하지 않는다 — 배포되지 않는 코드다.
- 속성 테스트는 "예제로는 못 덮는 불변식"에만 쓴다. 예제 하나로 충분한 시나리오에 속성 테스트를 쓰지 않는다(테스트 예산, 플러그인 adr/0034).

## 버린 대안

- **예제 기반 테스트로 대체**: 의존성이 없지만 조합 공간을 덮지 못한다. 정규화의 버그는 대개 "이 조합에서만"이라 예제가 놓치는 자리다.
- **`@fast-check/vitest` 래퍼**: `fc.assert(fc.property(...))`를 `it.prop`으로 줄여 줄 뿐이고 의존성이 하나 더 는다. 본체만 쓴다.
- **직접 만든 랜덤 생성기**: 축소(shrinking)가 없어 실패 재현이 어렵다 — 그 부분이 라이브러리의 본질이다.

## 감수한 트레이드오프

- devDependency 하나와 arbitrary 코드(수십 줄)를 유지한다. 생성기는 `doc.ts`의 닫힌 집합 상수(FONTS · MOTIONS · STICKER_IDS 등)를 그대로 가져다 쓰므로 값 하나가 늘면 자동으로 따라온다. 다만 노드 "종류"가 새로 생기면(예: 새 블록 타입) 생성기를 손으로 갱신해야 하고, 지금은 그 누락을 잡는 장치가 없다 — 픽스처 `allBlocks` 커버리지 테스트는 픽스처 자체가 모든 종류를 한 번씩 쓰는지만 검사할 뿐, arbitrary 생성기가 새 종류를 놓쳤는지는 보지 않는다.
- 속성 테스트는 실행 시간이 예제보다 길다(100회 기본). `pnpm verify`에 들어가므로 회당 수백 ms 수준을 유지한다.

## 재검토 조건

- 속성 테스트가 flaky하거나 verify 시간을 눈에 띄게 늘릴 때 — 실행 횟수 조정 또는 예제 기반으로 축소.
- fast-check가 12개월 이상 릴리스가 없을 때.
