# ADR-045. 배포 로그인 잠금은 누적(잠길 때마다 2배, 상한 24시간)이고 Supabase에 남는다

- 날짜: 2026-09-28
- 상태: 승인됨(사용자 2026-09-25 "긴 비밀번호 강제 대신 잠금 카운터" · #33 기본안 → #203)
- 관계: D8(긴 무작위 비밀번호가 방어의 중심)의 전제를 바꾼다. adr-018의 잠금 카운터(5회 → 15분, 메모리)를 확장한다 — 뒤집지 않는다. ADR-044(Supabase 배포)가 로그인을 공개로 만든다.

## 문제 (맥락)

배포하면 로그인 화면이 공개된다. 주인은 짧은 비밀번호(`1234` 류)를 쓰고 싶어 한다. 지금 잠금(5회 실패 → 15분, 풀리면 0부터)이면 15분마다 5번씩 꾸준히 시도해 4자리 숫자 1만 개를 평균 약 10일에 다 돈다. 게다가 카운터가 메모리라 서버리스 함수가 새로 켜질 때마다 초기화된다 — 배포에서는 사실상 잠금이 없다.

## 결정

- 5회 연속 실패 → 잠금은 그대로. **잠길 때마다 시간을 두 배로**(15분 → 30분 → 1시간 … **상한 24시간**). 잠금이 풀리면 연속 실패 수는 0부터 다시 세지만 **잠긴 횟수는 남는다**. 로그인에 성공해야 둘 다 0이 된다.
- 카운터는 잠금 저장소 규격(async) 뒤에 둔다 — 로컬은 메모리, 배포는 **Supabase Postgres `login_lockouts` 표**.
- **시도는 비밀번호를 확인하기 전에 실패로 먼저 센다**(맞으면 지운다). 세기와 잠금 확인은 DB 함수 하나(`record_login_failure`, 잠겨 있으면 세지 않고 false)가 행 잠금 아래 한 문장으로 한다 — 확인 뒤에 따로 세면 병렬 요청이 잠기기 전에 전부 비밀번호 판정을 받아 "5회" 상한이 무너진다(#203 코드 리뷰). 잠금 시간 계산의 지수는 30에서 자른다(수십 번 잠기면 곱이 bigint를 넘어 기록이 멈춘다).
- 주인 잠금 해제: `delete from login_lockouts;`(Supabase SQL 편집기) — `docs/deploy-supabase.md`.
- 배포 진입점은 비밀번호 **해시만** 받는다(평문은 로컬 `.env` 전용).

## 버린 대안

- **긴 비밀번호 강제(D8 그대로)**: 주인이 원하지 않는다(2026-09-25).
- **시간이 지나면 잠긴 횟수가 줄어듦(감쇠)**: 공격자는 기다리기만 하면 된다. 1단계는 본인 한 명이라 성공 리셋으로 충분하다.
- **IP별 잠금**: 공격자는 IP를 바꾼다. 계정 · "없는 아이디" 묶음 기준이 유지된다.
- **CAPTCHA · 2단계 인증**: 새 의존성 · 외부 서비스, 1단계엔 과하다.

## 감수한 트레이드오프

- **서비스 거부가 길어진다**: 아이디를 아는 사람은 주인을 최대 24시간 잠글 수 있다. 주인은 SQL 한 줄로 푼다. 추측하기 어려운 `ADMIN_USERNAME`을 권한다.
- **로그인 한 번에 DB 호출이 는다**(잠금 확인 + 기록) — 하루 한 번 쓰기라 무료 한도에 영향 없다.

계산: 몇 번 잠긴 뒤로는 하루 5번꼴(24시간 잠금)이라 1만 개를 다 도는 데 평균 약 3년.

## 재검토 조건

- 여러 사람이 쓰게 될 때(2단계) — 계정별 해제 UI · 알림
- 실제로 주인이 잠겨 불편을 겪을 때 — 감쇠 또는 해제 링크
