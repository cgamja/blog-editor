# ADR-003. 원본은 zod가 정의한 문서 JSON이고, markdown은 입력 전용이다

- 날짜: 2026-09-22
- 상태: 승인됨
- 원천: 설계 문서 D4 · 3-4 저장 형식 · D14 (닫힌 집합)

## 문제 (맥락)

지금 글은 markdown이다. 그런데 콜아웃 · 앱 스크린샷 프레임 · 글씨체 · 스티커 · 움직임 같은 것은 markdown에 자리가 없고, 확장 문법을 만들면 그 문법의 주인이 파서가 된다. 에디터 · 가져오기 · AI가 쓴 글 — 입구가 셋인데 저장되는 것은 하나여야 한다.

## 결정

- 저장 형식은 `{ schemaVersion, meta, doc }` JSON 하나. `doc`은 ProseMirror JSON과 호환이지만 **정의는 zod가 한다**(`content-schema`). `content-schema`는 ProseMirror를 모른다.
- **닫힌 집합**: 타이핑 · 붙여넣기 · markdown 가져오기 · AI가 쓴 markdown — 모든 입구가 서버에서 같은 zod 검증을 통과해야 저장된다. 링크는 `http(s):` · `mailto:` · 내부 경로만, 이미지는 `/images/` 경로만. 꾸미기 속성도 enum과 % 범위로 닫는다.
- **정규형 하나**: 마크 순서 고정 · 인접 텍스트 병합 · 키 순서 고정. 저장 버전끼리 비교하면 실제 변경만 보인다.
- `schemaVersion` + `migrations[n]: (v_n) => v_n+1` 순수 함수. 에디터에서 열 때와 공개 API가 렌더할 때 같은 함수를 쓴다.
- zod ↔ ProseMirror 스키마 일치는 속성 테스트로 묶는다: zod를 통과한 문서는 `Node.fromJSON(...).check()`도 통과한다.
- markdown은 가져오기와 MCP 도구의 **입력**이다. 내보내기는 1차 범위 밖.

## 버린 대안

- **markdown이 원본**: 확장 문법(`:::callout` 등)이 늘수록 파서가 곧 스키마가 된다. 꾸미기 속성(스티커 좌표 · 폭 %)을 markdown에 넣으면 사람이 못 읽는 markdown이 된다.
- **HTML이 원본**: 검증할 집합이 열려 있다(임의 태그 · 속성). sanitize에 의존하게 된다.
- **ProseMirror 스키마가 곧 저장 형식**: 저장 형식의 주인이 에디터 라이브러리가 된다. 서버(MCP 도구 · 렌더)가 에디터 없이 돌아야 하므로 정의는 라이브러리 밖에 둔다.

## 감수한 트레이드오프

- 스키마를 두 번 쓴다(zod + TipTap 확장). 속성 테스트가 둘의 어긋남을 잡는다.
- markdown 왕복이 완전하지 않다(doc → md → doc 보존 범위는 속성 테스트로 명시). 가져오기 화면이 손실 목록을 보여 준다.
- 스키마 버전 관리 비용. 사이트는 HTML만 받으므로 이 비용이 에디터 레포 안에 갇힌다(ADR-001).

## 재검토 조건

- 블록 종류가 20개를 넘어 zod와 TipTap 확장의 이중 정의가 부담될 때 — 한쪽에서 다른 쪽을 생성하는 방안 검토.
