# ADR-004. 글은 S3 객체 하나로 저장하고, `PostStore` 계약 뒤에 숨기며, 충돌은 `If-Match`로 잡는다

- 날짜: 2026-09-22
- 상태: 승인됨
- 원천: 설계 문서 D5 · 3-6 API · 3-7 글 수정 흐름

## 문제 (맥락)

글 수는 수십 편이고 쓰는 사람은 하루 한 번이다. 그런데 두 탭에서 같은 글을 열어 고치거나, 에디터에서 고치는 동안 AI가 같은 초안을 갱신하면 나중 저장이 먼저 저장을 조용히 덮는다. DB 없이 이것을 막을 수 있는가. 그리고 로컬 우선 개발(D12)에서 클라우드 없이 같은 코드를 돌릴 수 있는가.

## 결정

- 저장은 **S3(버저닝 켬)**. 키는 `workspaces/<workspaceId>/posts/<slug>.json`. 1단계에는 워크스페이스가 하나지만 경로는 처음부터 이렇게(ADR-007).
- `PUT /api/posts/:slug`는 `If-Match: <revision>` 필수. 어긋나면 **409**와 현재 revision. 화면은 「저장 충돌」 대화상자로 두 본문을 보여 준다.
- **revision은 불투명 문자열이고 주인은 `PostStore`다.** `get`이 돌려주고 `put`이 받으며, API는 그 값을 `ETag` 응답 헤더 / `If-Match` 요청 헤더로 그대로 실어 나른다 — 변환하지 않는다. `S3PostStore`는 S3가 준 ETag(따옴표 포함 원문)를 revision으로 쓰고 `put`에서 그대로 `IfMatch`에 넣는다(412 → `ConflictError`). `MemoryPostStore` · `FilePostStore`는 내용 해시를 revision으로 쓰고 직접 비교한다. 계약 테스트는 「`get`이 준 revision으로 `put`하면 성공, 낡은 revision이면 `ConflictError`」만 본다 — 형식은 보지 않는다.
- 저장소는 인터페이스 `PostStore { list · get · put(slug, file, revision | null) }` 하나. 구현은 Memory(테스트) · File(로컬 개발 · CI) · S3(운영). **셋이 같은 계약 테스트를 통과한다.**
- 이미지는 `images/<해시>.webp`로 같은 버킷. presigned POST에 크기 · 형식 조건.
- 계정 · OAuth 상태 · 연결용 토큰 해시는 DynamoDB 온디맨드(미검증 — 스파이크에서 S3만으로 되는지 본다).

## 버린 대안

- **RDB(RDS · Postgres)**: 글 수십 편에 서버 상시 비용. 문서가 JSON 하나라 관계형이 필요 없다.
- **DynamoDB에 글 저장**: 항목 400KB 제한이 긴 글에 걸릴 수 있다. S3 버저닝이 백업 · 되돌리기를 공짜로 준다.
- **Git 커밋으로 저장**: 서버가 레포 쓰기 권한을 가진다(ADR-001에서 폐기).
- **마지막 저장이 이김(충돌 무시)**: AI가 초안을 쓰는 순간부터 같은 글을 둘이 만지는 상황이 정상 경로가 된다.

## 감수한 트레이드오프

- S3는 목록 조회가 느리고 정렬 · 필터가 없다. 글 목록은 `list()`가 메타를 모아 준다 — 수백 편까지는 문제없고, 넘으면 목록 인덱스 객체 하나를 두면 된다.
- ETag 기반 낙관적 잠금은 「누가 이겼나」만 알려 주지 병합은 못 한다. 사람이 대화상자에서 고른다.
- 세 구현을 유지한다. 계약 테스트 스위트 하나가 셋을 돌므로 유지 비용은 테스트 한 벌이다.

## 재검토 조건

- 글이 수백 편을 넘거나 목록에 검색 · 정렬이 필요할 때 — 인덱스 객체 또는 DynamoDB 메타 테이블.
- M0 스파이크에서 S3 `If-Match` PUT이 412를 내지 않으면 DynamoDB 조건부 쓰기로 revision을 관리한다.
