# Spec Delta — backup-restore

## Purpose

무료 Supabase에는 받을 수 있는 자동 백업 · 시점 복구가 없다고 보고, 매일 DB와 사진을 Supabase 밖에 암호화해 두고 복구 절차를 주기적으로 검증한다(ADR-044 백업 · 복구).

## ADDED Requirements

### Requirement: 매일 DB 덤프와 사진을 암호화해 Supabase 밖에 둔다 (보호 대상)

백업 작업(GitHub Actions, 매일 · 수동 실행 가능)은 SHALL 운영 Postgres의 스키마 + 데이터 SQL 덤프와 사진 버킷의 모든 객체를 받아 하나로 묶고, 시크릿 암호(`BACKUP_PASSPHRASE`)로 대칭 암호화한 파일만 워크플로 아티팩트로 올린다(보관 90일). 레포가 공개라 암호화하지 않은 덤프 · 사진은 어디에도 올리지 않는다. 실패하면 작업이 빨간불이 되어 GitHub 알림이 간다.

#### Scenario: 올라간 백업은 암호 없이 읽을 수 없다

- **WHEN** 백업 작업이 끝난 뒤 아티팩트를 받는다
- **THEN** 파일은 암호화된 묶음 하나이고, 암호로 풀면 `dump.sql`과 `images/` 객체가 나온다

#### Scenario: 시크릿이 빠지면 작업이 실패한다

- **WHEN** `SUPABASE_DB_URL` 또는 `BACKUP_PASSPHRASE` 없이 작업을 돌린다
- **THEN** 아무것도 올리지 않고 빠진 이름을 알리며 실패한다

### Requirement: 복구 절차는 문서가 있고 분기마다 검증한다

복구는 SHALL 문서(`docs/deploy-supabase.md` 복구 절)의 순서 — 새(또는 비운) 프로젝트에 마이그레이션 → 덤프 복원 → 사진 다시 올리기 — 로 하고, 복구 검증 작업(분기마다 · 수동)은 최신 백업을 시험용 프로젝트에 복원해 글 수 · revision · 사진 수가 원본과 같은지 대조한다.

#### Scenario: 복구 검증이 원본과 같다

- **WHEN** 복구 검증 작업이 최신 백업을 시험용 프로젝트에 복원한다
- **THEN** 워크스페이스별 글 수 · 글마다 revision · 사진 수가 운영과 같다고 보고하고, 다르면 실패한다

실패 의미론: 응답 유실 · 동시 입력 해당 없음(읽기 전용 작업). 수명: 아티팩트 90일 보관 뒤 사라진다 — 그보다 오래된 시점으로는 되돌릴 수 없다.
