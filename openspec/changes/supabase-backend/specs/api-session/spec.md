# Spec Delta — api-session

## MODIFIED Requirements

### Requirement: 연속 실패가 쌓이면 로그인을 잠근다 (보호 대상)

로그인 확인(`POST /api/session`과 OAuth `POST /authorize`가 같은 함수를 쓴다)은 SHALL 한 계정에 연속 5회 실패하면 그 계정을 잠그고, **잠길 때마다 잠금 시간을 두 배로** 늘린다(15분 → 30분 → 1시간 …, 상한 24시간). 잠금이 풀리면 연속 실패 수는 0부터 다시 세지만 잠긴 횟수는 남는다. 성공하면 연속 실패 수와 잠긴 횟수가 모두 0이 된다. 잠긴 동안에는 비밀번호가 맞아도 틀린 로그인과 같은 응답(401 · 같은 메시지 · 같은 화면)이다. 없는 아이디는 모두 한 묶음으로 세어 잠금으로도 계정 유무가 드러나지 않는다. 카운터는 잠금 저장소(로컬 메모리 · 배포 Supabase Postgres)에 있고, 배포에서는 함수가 새로 켜져도 남는다. **비밀번호를 확인하기 전에** 시도를 실패로 먼저 세고(잠겨 있으면 세지 않고 거부), 맞으면 기록을 지운다 — 확인과 기록이 DB 안에서 한 문장이라 동시에 몇 개를 보내도 잠금 한 번에 비밀번호를 보는 시도는 5번까지다.

#### Scenario: 5회 실패 뒤에는 맞는 비밀번호도 거부된다

- **WHEN** 시드 아이디에 틀린 비밀번호로 5번 로그인한 뒤 맞는 비밀번호로 로그인한다
- **THEN** 401이고 `Set-Cookie`가 없다

#### Scenario: 잠금은 15분 뒤 풀린다

- **WHEN** 5번 실패해 잠긴 뒤 시계가 15분 넘게 흐르고 맞는 비밀번호로 로그인한다
- **THEN** 204다

#### Scenario: 두 번째 잠금은 30분이다

- **WHEN** 첫 잠금이 풀린 뒤 다시 5번 실패하고, 시계가 16분 흐른 뒤 맞는 비밀번호로 로그인한다
- **THEN** 401이고, 30분 넘게 흐른 뒤에는 204다

#### Scenario: 잠금 시간은 24시간을 넘지 않는다

- **WHEN** 잠금을 10번 거듭한다
- **THEN** 마지막 잠금은 24시간 뒤에 풀린다

#### Scenario: 성공하면 누적이 처음으로 돌아간다

- **WHEN** 두 번 잠긴 뒤 풀려서 맞는 비밀번호로 로그인하고, 다시 5번 실패한다
- **THEN** 이번 잠금은 15분이다

#### Scenario: 없는 아이디의 실패는 실제 계정을 잠그지 않는다

- **WHEN** 없는 아이디로 5번 실패한 뒤 시드 아이디 · 맞는 비밀번호로 로그인한다
- **THEN** 204다

#### Scenario: 병렬 실패도 빠짐없이 센다

- **WHEN** Supabase 잠금 저장소에 같은 키로 실패 5개를 동시에 기록한다
- **THEN** 그 키는 잠겨 있다

#### Scenario: 동시에 보내도 비밀번호를 보는 시도는 5번까지다

- **WHEN** 같은 키로 시도 10개를 동시에 기록한다
- **THEN** 정확히 5개만 "확인해도 된다"를 받고 나머지는 거부되며, 그 키는 잠겨 있다

#### Scenario: 잠금을 아무리 거듭해도 오류 없이 24시간이다

- **WHEN** 잠금을 60번 거듭한다
- **THEN** 기록이 실패하지 않고 마지막 잠금은 24시간 뒤에 풀린다

실패 의미론: 아이디를 아는 사람은 거듭 틀려 그 계정을 최대 24시간 잠글 수 있다(서비스 거부 비용을 받아들인다) — 주인은 문서의 SQL 한 줄로 잠금을 푼다(`docs/deploy-supabase.md`). 로컬 메모리 카운터는 재시작하면 초기화된다. 응답 유실 재시도는 실패 한 번으로 세어도 무방하다. 시도를 먼저 세므로, 맞는 비밀번호인데 기록 지우기(DB)가 실패하면 로그인은 오류이고 그 시도는 실패로 남는다(최악은 5번째 시도에서 15분 잠김 — 주인은 SQL로 푼다).
