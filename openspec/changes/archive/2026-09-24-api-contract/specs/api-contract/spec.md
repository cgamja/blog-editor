## ADDED Requirements

### Requirement: `/api` 계약은 코드에서 내보낸 파일 하나다

`api/openapi.json`은 SHALL `apps/editor/api`의 계약 스키마 표에서 `buildOpenApiDocument()`로 만든 OpenAPI 3.1 문서와 깊이 같다. 파일을 손으로 고치지 않고, 스키마를 바꾸면 내보내기 명령으로 다시 쓴다.

#### Scenario: 커밋된 계약이 코드와 같다

- **WHEN** 계약 스키마 표로 문서를 다시 만든다
- **THEN** 커밋된 `api/openapi.json`을 읽은 값과 깊이 같다

### Requirement: 앱의 라우트는 계약에 있는 것뿐이다

`createApp`에 등록된 라우트(미들웨어 · `/mcp` · OAuth 제외)의 메서드와 경로는 SHALL 계약의 경로 · 메서드와 같은 집합이다. 계약에 없는 라우트를 더하면 테스트가 실패한다.

#### Scenario: 라우트 목록과 계약이 같다

- **WHEN** 이미지 저장소를 켠 앱의 라우트를 모은다
- **THEN** `{메서드, 경로}` 집합이 계약의 것과 같다

### Requirement: 응답은 선언된 상태 코드와 그 스키마를 따른다

각 라우트의 응답은 SHALL 계약에 선언된 상태 코드 중 하나이고, JSON 본문은 그 상태의 스키마를 통과한다. 본문이 없는 204와 바이너리 · CSS 응답은 선언된 `Content-Type`을 따른다.

#### Scenario: 로그인 · 로그아웃 응답이 계약을 따른다

- **WHEN** 맞는 계정, 틀린 비밀번호, 빠진 필드, JSON이 아닌 본문으로 로그인하고 로그아웃한다
- **THEN** 차례로 204 · 401 · 400 · 400 · 204이고 오류 본문이 메시지 스키마를 통과한다

#### Scenario: 글 목록 · 읽기 · 저장 응답이 계약을 따른다

- **WHEN** 세션 없이 목록을 부르고, 새 글 저장 · 고쳐 저장 · 낡은 revision 저장 · 조건 헤더 없는 저장 · 스키마 위반 저장 · 없는 글 읽기 · 잘못된 주소 읽기 · 목록 · 읽기를 한다
- **THEN** 401 · 201 · 200 · 409 · 428 · 400 · 404 · 400 · 200 · 200이고 각 본문이 그 상태의 스키마를 통과한다

#### Scenario: 이미지 · 공개 응답이 계약을 따른다

- **WHEN** PNG를 두 번 올리고, SVG · 큰 파일 · 긴 변 초과를 올리고, 올린 이미지 · 없는 이미지를 받고, 공개 목록과 본문 CSS를 받는다
- **THEN** 201 · 200 · 415 · 413 · 422 · 200 · 404 · 200 · 200이고 JSON 본문은 스키마를, 나머지는 선언된 `Content-Type`을 따른다

실패 의미론: 해당 없음 — 계약은 읽기 전용 문서이고 라우트 동작은 바꾸지 않는다.
